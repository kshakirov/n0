# Первый контакт с Node-API

Я начал с простого вопроса: как Node.js может вызвать код, написанный на Rust, если Node обычно показывает нативные модули на C и C++?

## Где встречаются Node и Rust

После компиляции языковой синтаксис исчезает. На границе остаётся машинный договор: имена символов, расположение данных и правила передачи аргументов и результатов.

Я разделяю три понятия:

```text
API — как я вызываю функцию в исходном коде
ABI — как бинарные компоненты вызывают друг друга в машинном коде
ELF — как машинный код и таблицы символов упакованы в файл на Linux
```

Node-API — это стабильный C ABI, который предоставляет сам Node. Node внутри работает с C++ и V8, мой модуль написан на Rust, но на общей границе обе стороны соблюдают правила C ABI:

```text
JavaScript
    ↕
Node.js / V8
    ↕ Node-API, C ABI
Rust dynamic addon
```

В Rust я описываю эту границу через `extern "C"`. Для Node результат сборки является динамической библиотекой с ожидаемой точкой входа `napi_register_module_v1`.

## Непрозрачные значения

JavaScript-значение приходит в Rust как `NapiValue`:

```rust
type NapiValue = *mut c_void;
```

Это непрозрачная ручка. По самому указателю я не могу восстановить JavaScript-тип, поэтому спрашиваю Node через его API. Например, `napi_is_buffer` сообщает, является ли значение объектом `Buffer`.

## Зачем нужны указатели на результат

Функция Node-API часто возвращает `NapiStatus`, чтобы сообщить, успешно ли прошла операция. Полезный результат она записывает отдельно по переданному адресу.

Для проверки буфера я создаю обычную изменяемую Rust-переменную:

```rust
let mut result = false;
```

и передаю `&mut result`. Node записывает ответ в эту существующую ячейку памяти:

```text
возвращаемое значение функции → статус операции
выходной указатель           → true или false
```

`NapiValue` уже является указателем, поэтому `*mut NapiValue` соответствует привычному C-типу `void **`: это адрес ячейки, в которую Node запишет новую ручку.

## Почему Rust bool нельзя вернуть прямо в JavaScript

Машинный `bool` и JavaScript Boolean принадлежат разным системам представления. Я не привожу один тип к другому. Через `napi_get_boolean` я прошу Node создать соответствующее JavaScript-значение:

```text
Rust bool
→ napi_get_boolean
→ JavaScript Boolean внутри Node
→ NapiValue
```

Локальная Rust-переменная после этого остаётся обычным `bool`. Возвращаемый `NapiValue` — отдельная ручка на значение, которым управляет Node.

## Как я получил память Buffer

`napi_get_buffer_info` принимает два входа — среду и `NapiValue` — и два выходных параметра:

```text
void**  data   → место, куда Node записывает адрес первого байта
size_t* length → место, куда Node записывает длину в байтах
```

Я сначала проверил только длину, а затем передал адрес Rust-переменной `*mut c_void` и получил реальный адрес данных. Перед чтением я проверяю два условия: длина больше нуля и указатель не равен `null`.

Разыменовав `data.cast::<u8>()`, я прочитал первый байт непосредственно из памяти Node Buffer. При этом важно различать значение и место: запись прочитанного байта в локальную Rust-переменную создаёт копию и не изменяет Buffer. Для изменения нужно писать по исходному адресу либо построить временный `&mut [u8]`.

## Что уже доказано

Я собрал Rust как `cdylib`, загрузил его из Node как файл `.node`, экспортировал функцию `isBuffer`, получил аргумент через `napi_get_cb_info`, проверил его через `napi_is_buffer`, вернул JavaScript Boolean, получил длину Buffer и прочитал его первый байт по сырому указателю.

Следующий шаг — записать байт по полученному адресу, затем временно представить всю область как Rust-срез и проверить изменение тех же байтов без копирования.
