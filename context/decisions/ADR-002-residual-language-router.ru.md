# ADR-002 — Потоковый маршрутизатор на остаточных языках

[English](ADR-002-residual-language-router.en.md) · [Все решения](README.md)

Проект: N0. Статус: **Proposed — принято к экспериментальной реализации**.
Дата: 2026-11-23. Компонент: Rust URI Router. Ветка: `dev-optimized`.

## Контекст

Я хочу выбирать маршрут непосредственно при последовательном чтении URI, начиная с одного байта. Сохраняю все допустимые альтернативы, исключаю несовместимые, поддерживаю параметры переменной длины и избегаю повторного сканирования URI. Временные структуры и аллокации стремлюсь уменьшить, но их стоимость ещё предстоит измерить.

Я рассмотрел Radix/Trie, хеширование, производные Бжозовского и булеву матричную алгебру. Для первого эксперимента выбираю собственное представление остаточного языка. Код и формат ещё не испытаны; это не решение о готовности к эксплуатации.

## Математическая основа

Для языка маршрутов L и прочитанного префикса p:

```text
D_p(L) = { w | pw ∈ L }
```

Это множество допустимых продолжений. Представляю его активными маршрутами и их рабочими состояниями; классические производные регулярных выражений непосредственно не вычисляю.

## Решение для эксперимента

### Компиляция и идентичность

JS задаёт маршруты и хранит функции обработчиков. Rust получает байтовое представление и возвращает исходный RouteID; JS вызывает соответствующую функцию. На концептуальном уровне маршруты и обработчики связаны параллельными массивами:

```rust
routes: Vec<Vec<u8>>
handlers: Vec<Handler>
```

`Handler` здесь обозначает ссылку на обработчик в JS, а не утверждённый Rust-тип. При необходимости сортирую маршруты один раз при компиляции, сохраняя исходные RouteID независимо от позиции после сортировки.

### Параметры

Компилирую параметр в специальную область маршрута, первоначально размером 128 байт, заполненную маркером `{`. Сохраняю имя параметра и границы области. `/` — выделенный разделитель сегментов. Правила буквального `{`, кодированных разделителей и точный формат ещё не определены.

### Рабочий набор и сопоставление

Для запроса создаю независимый набор изменяемых кандидатов; скомпилированные маршруты сохраняю неизменными:

```rust
struct Candidate {
    route_id: usize,
    bytes: Vec<u8>,
}

active.retain_mut(|candidate| step(candidate, byte));
```

Это набросок, не полный формат состояния. На каждом байте `step` проверяет ожидаемую позицию: буквальное совпадение сохраняет альтернативу, несовпадение исключает её, область параметра принимает байт. На `/` завершаю параметр и переключаю адресацию на следующий сегмент. Индексы и метаданные определю в прототипе.

### Адресация

Использую идею `route[base + offset]`: offset отражает продвижение по входу, base переключает области без физического перемещения суффикса. Для параметров предполагаю фиксированную область метаданных о следующем участке. Её формат и механизм переключения ещё экспериментальные.

### Завершение и результат

Совместимость с префиксом ещё не означает полного совпадения. На конце URI проверяю принятие всего пути, затем разрешаю оставшиеся альтернативы. Результат содержит исходный RouteID, рабочее состояние и захваченные параметры. Приоритет статических и параметризованных маршрутов определю отдельно.

## Инвариант

После n байтов набор содержит все и только те маршруты, которые допускают прочитанный префикс:

```text
Active_(n+1) = Step(Active_n, b_n)
```

Проверяю этот инвариант исполняемой программой, сопоставляя кандидатов с допустимостью префикса, а не только проверяя конечный ответ. `retain_mut` не возвращает удалённые альтернативы, поэтому ошибочное раннее исключение недопустимо.

## Проверки прототипа

Начальные маршруты:

```text
/users/{id}/name
/update/name
/users/add/
/mail/user/{id}/reset
```

Проверю буквальные совпадения и исключения, одновременные статические и параметризованные альтернативы, разные длины и несколько параметров, пустые и слишком длинные значения, завершение URI внутри параметра, побайтовый вход и произвольные разбиения. Проверю границы массивов, инвариант на каждом префиксе и неизменность соответствия RouteID обработчику.

## Открытые вопросы

- Формат префикса и метаданных параметра; переключение base.
- Переполнение 128-байтовой области: правило ещё не выбрано.
- Разрешение нескольких полных совпадений и разделение статических/параметризованных маршрутов.
- Стоимость копирования рабочих маршрутов и повторное использование памяти.
- Граница URI и query string, кодирование и учёт HTTP-метода.

## Альтернативы

Radix/Trie не выбираю для первого эксперимента. Хеширование само по себе не задаёт потоковую обработку параметров. Производные Бжозовского использую как математическую основу, но не как буквальное представление данных. Булеву матричную алгебру оставляю отдельным исследованием для Haskell Proxy.

## Принцип

Маршрутизация последовательно сокращает множество допустимых продолжений URI. Программа реализует преобразование и проверяет его инварианты. Принятие экспериментального направления не означает доказанную корректность или преимущество в производительности.
